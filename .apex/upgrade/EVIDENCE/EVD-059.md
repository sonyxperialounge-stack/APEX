# EVD-059 — ExecutionContext on the operation record (WP-059)

Date: 2026-09-11 · Packet: WP-059 (54 §13) · Branch: upgrade/army-v4

## Context

54 §13 defines five execution contexts (`local`, `worktree`, `container`,
`remote`, `unknown`), requires the Operation record to carry one (absent ⇒
`unknown`, governed as `local`), and requires every audit event and
verification record to carry the context the work ran in. Accepted tests:
CAP-T08 (no declared context → governed as local) and CAP-T09 (audit and
verification evidence carry execution context).

## What was built

- `~src/core/types.ts`: `EXECUTION_CONTEXTS` const + `ExecutionContext` type
  between `CapabilityEffect` and `Operation`; `Operation.context?` (absent ⇒
  `unknown` ⇒ governed as `local`); `VerificationRecord.context` (required,
  defaults `local` on load-down of legacy records).
- `+src/core/context.ts`: `detectExecutionContext(cfg)` — container env
  markers first, then `delegation.isolation === "worktree"`, then remote CI
  markers, else `local`. Never fabricates `unknown`; an unclassifiable
  environment is still `local` (the most conservative answer).
- `~src/engines/governor.ts`:
  - `normalizeContext()` (absent/`unknown` → `local`; CAP-T08) and
    `renderContext()` (absent → `"unknown"` label).
  - `modePolicy` computes `normalizeContext(op.context)`; a disposable
    `container`/`worktree` is the ONLY relaxation: GUARDED allows a risky op
    ("throwaway container/worktree — disposable state, nothing persistent at
    risk"), FULL_AUTO/AUTO allow a DESTRUCTIVE op there with the snapshot bar
    intact. The hard RULES blocklist runs first and never relaxes with
    context. `local`/`remote`/`unknown` keep every existing bar.
  - `governor.block` events now carry `context: renderContext(op.context)`;
    `governor.snapshot` and `governor.rollback` carry the process-level
    `detectExecutionContext(this.cfg)`.
- `~src/engines/ledger.ts`: `addVerification` accepts optional `context`
  (recorded as `local` when absent — the conservative default); reads default
  `local` for pre-existing records; the rendered VERIFICATION.md detail lines
  now include `- **Context:** <value>`.
- `~src/engines/verifier.ts`: `cascade` and `diagnosticsRecords` capture
  `detectExecutionContext(this.cfg)` once per cascade and stamp it on every
  record (CAP-T09).
- `~src/mcp/tools.ts`: `apex_check` schema gained a `context` enum parameter
  (`local|worktree|container|remote`) and forwards it onto the Operation;
  absent stays `unknown` → governed as `local`.

## Surprises

1. `apex_init` on an existing ledger is a NO-OP for config — the MCP test
   tried to add `doNotTouch` on a second init and it silently did nothing;
   the first init carries all config.
2. The rendered line is `- **Context:** container` (bold markers) — an
   `includes("Context: container")` assertion can never match.
3. My first DESTRUCTIVE test over-asserted: `worktree`/`container` are by
   definition the ONLY relaxing contexts (54 §13), so "must never relax"
   applies to `local`/`remote`/`unknown` only.
