# EVD-045 — WP-041b fallbackFor + requiresEnvironment activation

Date: 2026-09-11
Branch: upgrade/army-v4

## Context

Inspection found `fallbackFor` + `requiresEnvironment` support ALREADY present in the tree
(the model that closed WP-043/047 also implemented the 54 §5/§6 surface, with SKL-T06/T07
tests in `skill-activation.test.ts`). WP-041b was still PENDING in STATE.json, so the
packet's remaining work was the missing enforcement pieces:

1. **SEC-T09 value rejection** — a `value:` key smuggled into a `requiresEnvironment`
   declaration must never be parsed. The parse regex admits only `name`/`why`/`required`,
   so a `value:` entry fails to match and is dropped whole (verified by test; the first
   draft added an explicit `value:`-scanner, which the audit then removed as dead code —
   the regex already guarantees it).
2. **Banned env names (54 §6)** — a declared name containing a provider-credential token
   (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `CREDENTIAL`, `ACCESS_KEY`, `CLIENT_SECRET`,
   `PRIVATE_KEY`, `API_KEY`, `AUTH`, `BEARER`, ...) is rejected at validation with a named
   error, so the declaration surface can never become a secret-collection surface.
3. **No code path reads env VALUES** — verified by sweep: the only environment interaction
   in skill code is `envPresent(name) => boolean` (skill-activation.ts), and no
   `process.env` access exists in any skill module (grep exit 1).
