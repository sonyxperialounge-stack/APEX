# EVD-049 — WP-049c bundles, 3-body limit, skills run/pin CLI

Date: 2026-09-11
Branch: upgrade/army-v4

## Context

54 §8 was MISSING: nothing said how a skill is actually invoked. Implemented the
model-facing selection surface and the bundle layer:

1. **Bundle store** — `src/stores/skill-bundles.ts`: a bundle is a named list of skills
   plus one instruction line at `<home>/skills/.bundles/<name>.json`. A bundle name
   resolves BEFORE an individual skill name. Lookup of a non-bundle name is simply "no
   such bundle", never an error (a slash-bearing skill id must be able to fall through).
2. **Composer engine** — `src/engines/skill-composer.ts`: `composeSkillInstruction`
   loads at most `maxBodies` (default 3, 54 §8) skill bodies for one task and makes the
   choice EXPLAINABLE — every loaded body carries its id, name, and the reason
   (named-skill vs bundle-member, with the description). A missing bundle member is
   skipped and REPORTED, never fatal (SKL-T12); a body dropped by the cap is reported
   too (SKL-T11). The result is a composed instruction block — it never executes
   anything.
3. **CLI surface** — `apex-agent skills run <name-or-bundle> [instruction]` prints the
   composed block; `skills bundle list|create|delete` manages bundles. `run` states
   plainly that it composes and never executes.
4. **Config** — `skills.maxBodiesPerTask` and `skills.seedSkills` added to ApexConfig
   (54 §20), with defaults (3 / true), normalisation in ledger init + loadConfig, and
   the templates/config.json block.

Root-cause fix during the pass: the bundle `read` threw on names that cannot BE bundles
(slash-bearing skill ids) — a lookup of a skill name would have crashed the composer.
`read` now returns null for any name that fails the bundle-name rule; only `save`
validates.
