# EVD-055 — Capability loss recovery (WP-055)

Date: 2026-09-11 · Packet: WP-055 · Branch: upgrade/army-v4 · Dep: WP-054

## Context

21 §10: a capability that fails structurally is handled with an honest
recovery ladder — mark, bounded refresh, safe-equivalent search, re-plan,
or report UNAVAILABLE with fallback. "Never keep issuing pretend calls to
a missing tool." 27 §5: stop → observe → classify → refresh only the
affected assumption → consult trap/skill → re-plan with a materially
different action → verify → escalate. 27 §14: every recovery carries a
`FAIL-…` id, a failure class, an attempt fingerprint (hash of
action-kind + normalized command + cwd + inputs + env, 27 §4), the chosen
recovery action, an outcome, and evidence ids. CAP-T06: a disconnect
invalidates stale availability without a daemon. RCV-T04: a host
disconnect triggers a *bounded* registry refresh — once per normalized
reason, never polling.

## What was built

- `~runtime/src/engines/capability-registry.ts`:
  - `markStructuralFailure(id, observed)` — labels the selected descriptor
    `DEGRADED` with `reason`; returns the marked descriptor or null (an
    already-unavailable capability cannot be downgraded twice). DEGRADED is
    transient: only a fresh re-registration lifts it back to AVAILABLE;
    a bounded refresh that does not revive it leaves it non-selectable.
  - `invalidateProviderAvailability(providerId, reason)` — CAP-T06: every
    non-UNAVAILABLE descriptor of the provider becomes UNAVAILABLE with the
    reason, no daemon required; returns the count changed.
  - `refresh(reason)` now returns `Promise<boolean>` — true when the
    bounded refresh hook actually ran, false when the reason was already
    refreshed (RCV-T04: callers can distinguish re-probe from suppression).
  - `StructuralFailureKind` (`not_found` / `disconnected` /
    `call_not_issued`), `isStructuralFailure({notFound, disconnected,
    callIssued})`, `attemptFingerprint(input)` = first 16 hex of sha256
    over action-kind + normalized command + cwd + inputs + env (27 §4).
  - `handleStructuralFailure(input, opts)` — the 21 §10/27 §5 ladder:
    mark → `await refresh("structural-failure:<id>")` (bounded, returns
    after the first refresh per reason) → select a safe equivalent. An
    equivalent must be AVAILABLE and its effects must cover the ORIGINAL
    effects set — the repair never papers over a missing effect
    (DELETE/DESTRUCTIVE cannot be replaced by a READ, 21 §10). The caller
    may supply `findEquivalent` (the WP-053 search seam), but any claimed
    hit is still effects-gated. Outcome:
    - `RECOVERED` + same provider/tool → reboot ("recovered (available)
      after a bounded refresh"),
    - `RECOVERED` + different conductor → re-plan ("re-planned onto safe
      equivalent <id>"),
    - `BLOCKED` → "UNAVAILABLE after a bounded refresh … report it and use
      the stated fallback",
    - `IGNORED` when nothing was available to lose — no refresh, no
      manufactured evidence.
    Recovery record: `{failureId: "FAIL-…", class:
    "CAPABILITY_UNAVAILABLE", capabilityId, observed, attemptFingerprint,
    recoveryAction, outcome, evidenceIds, createdAt}` (27 §14).
- `~runtime/src/engines/warden.ts`:
  - `replanAfterCapabilityLoss(packet, loss, replacement)` — WAR-006/007/008:
    appends a PROGRESS.md entry with the recovery record, emits
    `warden.replan`, increments `attempt`, carries forward survived work
    (`alreadyExists` else the objective when checkpointing), sets
    `strategyChange` from the module-level `strategyChangeForLoss(loss)`
    (RECOVERED/BLOCKED/IGNORED), and amends the objective with the
    explicit instruction "Do not re-issue the failed call" — re-planning
    onto the equivalent or running the stated fallback, never re-issuing
    the failed call (21 §10).
- `~runtime/src/plugin/index.ts`: host capability-change discovery now
  routes through `registry.refresh(reason)` (the bounded, deduped refresh)
  instead of an unbounded direct re-register.

## Surprises

1. The first warden assertion read `path.join(dir, "PROGRESS.md")`, but the
   ledger writes under `.apex/` inside the project root (LED-001) — the
   file existed, at `ledger.file("PROGRESS.md")`. The assertion now reads
   through the ledger's own path, like every other test in the suite.
2. `refresh`'s shape change (void → `Promise<boolean>`) rippled into the
   plugin discovery wiring — the host-change handler needed the `void`
   wrapper once the promise became meaningful.
3. A same-provider + same-tool revival reports a reboot, not a re-plan —
   `replanned` means a DIFFERENT conductor, which is the only case a warden
   needs to re-plan for.
