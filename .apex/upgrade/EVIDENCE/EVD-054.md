# EVD-054 — Lazy schema cache (WP-054)

Date: 2026-09-11 · Packet: WP-054 · Branch: upgrade/army-v4 · Dep: WP-053

## Context

22 §8: deferred schemas validate before use — parseable, no recursive/
unsupported constructs, raw kept for inspection, backend keeps final
contract, nothing silently coerced. 22 §9: session cache keyed
`providerId + toolName + schemaHash`; invalidate on provider disconnect,
schema hash change, structural tool/schema-not-found, explicit refresh;
never write discovered schemas into global memory. 41 §14 provides the
`ToolSchemaCache` blueprint. Acceptance: TLS-T02 (deferred schema absent
from the startup prompt), TLS-T03 (selected schema loads on demand, cached
per hash), TLS-T04 (cache invalidates on disconnect/hash drift).

## What was built

- `~src/engines/capability-search.ts` — the WP-054 layers:
  - `ToolSchemaCache` (session-only, in-memory): entries under
    `providerId:toolName` (the discovery pipeline always sets `toolName`;
    structural hash records what was loaded). `get(cap, load, expectedHash)`
    serves the cache without touching the loader on a hit; a host-reported
    `expectedHash` that differs from the stored fingerprint replaces the
    stale entry (hash drift = invalidation, TLS-T04). `invalidate(cap)` and
    `invalidateProvider(providerId)` sweep single entries / whole providers
    (disconnect, 22 §9). No disk, no global memory.
  - `validateDeferredSchema(raw)` (22 §8): accepts objects (JSON strings
    parse first); rejects non-object roots and internal `#/…` `$ref`
    pointers that do not resolve — and any `$ref` cycle (recursive
    constructs the local validator cannot safely handle). External refs stay
    the backend's contract (22 §8 #5). Throws `CAPABILITY_SCHEMA_INVALID`
    (45 §2.6), raw schema retained for inspection by the caller.
  - `schemaHashOf(schema)`: structural fingerprint — sha256 of the canonical
    JSON, first 8 hex (22 §9 "actual structural schema hash where
    available").
  - `CapabilitySearch.loadSchema(id, load, expectedHash?)` — the 22 §3
    Level-C door: resolves via `registry.select`, throws
    `CAPABILITY_UNAVAILABLE` for missing/unavailable capabilities (a schema
    is never fabricated, TLS-T07), then delegates to the cache with the
    caller-supplied loader (host adapter / WP-058 bridge; this engine never
    probes on its own, TLS-T05 spirit).
  - `CapabilitySearch.invalidateSchemaProvider(id)` /
    `invalidateSchema(id)` — the explicit refresh paths (22 §9).
- `~test/engines/capability-search.test.ts` — 16 new tests (34 total in the
  file): TLS-T02 (compact-index entries carry only id/summary/effects, never
  a schema), TLS-T03 (loader consulted exactly once, cache wins over a
  would-be replacement), TLS-T04 (hash drift reloads), provider disconnect
  sweep with an untouched other provider, missing/unavailable capability
  refusals, validator contracts (parse gate, object gate, `$ref` resolution,
  cycle rejection, acyclic acceptance), `schemaHashOf` canonicality, and
  per-capability invalidation.

## Surprises

1. The first cache-key draft used `providerId:toolName` correctly (41 §14)
   but the test fixture left `toolName` undefined, so `host.a`/`host.b`
   collided under `host:` — realistic descriptors (discovery always names
   the tool) fixed the tests, not the key.
2. An unparseable non-JSON string ("str") is caught by the JSON gate with
   the "not valid JSON" message, not the object gate — the assertion regex
   had to accept both paths.
