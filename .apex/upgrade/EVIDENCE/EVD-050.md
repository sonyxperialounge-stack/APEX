## What landed

1. **One effects taxonomy** (`21 §3`): `CAPABILITY_EFFECTS` as an `as const` array plus
   the `CapabilityEffect` union in `src/core/types.ts` (HC-001 — no enum), exactly the
   eight effects from `21 §3`. This is the single canonical vocabulary for registry,
   skills and security policy (CAP-T07 shows no parallel synonym exists).
2. **`toOperationKind`** — the ONE effect→`OperationKind` adapter, living in
   `governor.ts` (42 §6, correcting 21 §6's plan-time names). Mapping:
   READ→read · WRITE→write · EXECUTE/INSTALL→bash · NETWORK→network · DELETE→delete ·
   EXTERNAL_SIDE_EFFECT→deploy · composites → most restrictive kind, with EXECUTE
   winning so command-safety rules still see exec-based deletes/installs ·
   DESTRUCTIVE alone → delete.
3. **`isDestructive`** — DESTRUCTIVE is a MODIFIER, never a kind (42 §6). The adapter
   strips it and computes kind from the rest; the Governor receives `destructive: true`
   on the Operation.
4. **Governor enforcement** — `Operation.destructive?: boolean`, and `modePolicy`
   treats it as a modifier: raises `requiresSnapshot` and forces explicit approval in
   EVERY mode including FULL_AUTO (a destructive read in FULL_AUTO is refused, not
   allowed). Release scope: `Operation.destructive` is additive; no call site changed.

## Surprises

Two of my own test expectations were wrong before the code was — a composite
EXECUTE+DELETE must stay on `bash` (the command blocklist reasons on `op.command`),
so a pure kind-precedence view is the unsafe one; and "most restrictive kind" is not
a linear order when command detection is involved. The implementation was corrected
to keep exec-based operations visible to the command blocklist even when they also
delete or touch the network — that is the invariant 42 §6 cares about.
